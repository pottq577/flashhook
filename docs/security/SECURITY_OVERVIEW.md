# FlashHook Security Overview

FlashHook은 회원가입 없이 임시 웹훅 URL을 발급하는 서비스입니다. 그래서 전통적인 계정 인증보다 URL 토큰, 짧은 데이터 보존, 요청 빈도 제한, 외부 발송 방어를 조합해 남용 위험을 낮춥니다.

이 문서는 공개 레포에 노출해도 되는 보안 설계의 큰 방향만 설명합니다. 운영 임계치, Redis 키 패턴, 차단 기준 같은 세부 정책은 공개하지 않습니다.

## 1. URL 토큰 분리 전략

FlashHook의 URL은 역할이 분리되어 있습니다.

| URL 유형 | 용도 | 공개 여부 |
| --- | --- | :---: |
| Webhook 수신 URL | 외부 서비스가 웹훅을 전송하는 주소 | 공개 가능 |
| Dashboard URL | 수신 로그를 조회하고 설정을 변경하는 주소 | 비공개 토큰 필요 |

수신 URL은 외부 서비스에 등록되어 노출될 수 있습니다. 하지만 대시보드 접근, 로그 조회, 설정 변경, 삭제 같은 작업은 별도 `accessToken` 검증을 거칩니다.

## 2. Access Token 저장 방식

엔드포인트 생성 시 서버는 공개 식별자인 `endpointId`와 비공개 접근 토큰인 `accessToken`을 함께 발급합니다.

- 원본 `accessToken`은 생성 응답에서 1회만 반환됩니다.
- 서버는 원본 토큰을 저장하지 않고 SHA-256 해시만 보관합니다.
- 이후 인증 요청이 들어오면 요청 토큰의 해시와 저장된 해시를 비교합니다.

프론트엔드는 대시보드 진입 직후 URL에 포함된 토큰을 브라우저 주소창에서 제거하고, 탭 단위 임시 저장소에 보관해 의도치 않은 공유를 줄입니다.

## 3. Replay SSRF 방어

Replay 기능은 저장된 웹훅 요청을 사용자가 지정한 목적지로 다시 전송합니다. 외부 URL로 서버가 직접 요청을 보내는 기능이므로 SSRF(Server-Side Request Forgery) 방어가 필수입니다.

FlashHook은 Replay 요청 전 목적지 호스트를 해석하고, 다음과 같은 내부망 또는 특수 목적 주소로의 발송을 차단합니다.

- 사설 IP 대역
- 루프백 주소
- 링크 로컬 주소
- 기타 서버 내부 자원 접근에 악용될 수 있는 주소

또한 DNS Rebinding을 줄이기 위해 해석된 IP를 요청 시점에 고정하는 IP Pinning 방식을 사용합니다.

## 4. 동적 프리셋 시크릿 보호

GitHub, PortOne 같은 동적 프리셋은 서명 생성에 사용되는 시크릿 키를 받을 수 있습니다. 이 값은 평문으로 저장하지 않습니다.

- 저장 시 AES-256 기반으로 암호화합니다.
- 복호화는 런타임에서 서명 생성이 필요한 순간에만 수행합니다.
- 사용 후 원본 값은 장기 보관하지 않습니다.

이 구조는 데이터베이스가 노출되더라도 외부 연동 시크릿이 곧바로 평문으로 드러나는 위험을 낮추기 위한 방어선입니다.

## 5. 요청 빈도 제한

FlashHook은 회원가입 없이 사용할 수 있으므로 요청 빈도 제한을 적용합니다.

- 엔드포인트 생성 요청은 단기간 과도하게 반복될 경우 제한됩니다.
- 웹훅 수신 요청은 엔드포인트 단위로 빈도가 제한됩니다.
- Replay 요청도 남용 방지를 위해 제한됩니다.
- 비정상 트래픽은 운영 정책에 따라 차단될 수 있습니다.

정확한 임계치와 내부 키 구성은 우회 전략으로 악용될 수 있어 공개하지 않습니다.

## 6. 데이터 보존 원칙

FlashHook은 장기 보관 서비스가 아니라 임시 디버깅 도구입니다.

- 엔드포인트와 로그는 24시간 후 자동 파기됩니다.
- 사용자는 대시보드에서 엔드포인트와 로그를 직접 삭제할 수 있습니다.
- 로그 저장량은 서비스 안정성을 위해 제한됩니다.

자세한 개인정보 처리 기준은 [개인정보처리방침](../legal/PRIVACY_POLICY.md)을 참고해 주세요.

## 7. 공개하지 않는 운영 정보

아래 정보는 공개 문서에 포함하지 않습니다.

- Redis 키 네이밍 패턴
- 요청 제한의 정확한 임계치
- 차단 목록의 내부 키잉 방식
- 공격 벡터와 대응을 1:1로 매핑한 전체 운영표

기존 보안 정책 문서가 이미 원격 저장소에 올라간 경우, 파일 삭제만으로 git 히스토리에서 사라지지는 않습니다. 히스토리에서 완전히 제거하려면 `git filter-repo` 또는 BFG Repo-Cleaner를 이용한 별도 이력 재작성과 강제 푸시가 필요합니다. 이 작업은 파괴적이므로 사용자 확인 후 별도 진행해야 합니다.
