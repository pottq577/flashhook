# ADR 0003: Mock API 프리셋의 스펙 불일치(Drift) 완화 전략

## Context

FlashHook은 외부 서비스(카카오, 토스페이먼츠 등)의 응답을 그대로 재현하는 Mock API 프리셋을 제공합니다. 하지만 외부 서비스의 스펙은 지속적으로 변경되며, FlashHook의 하드코딩된 정적(static) 프리셋과 실제 스펙 간의 불일치(Drift)가 필연적으로 발생합니다.
초기 설계에서는 `status: "verified"`와 같은 이분법적 상태값으로 신뢰성을 보장하려 했으나, "실제 대상 API가 언제 변경될지 시스템이 추적할 수 없으므로, 완벽한 검증(Verified) 상태를 영구적으로 확신할 수 없다"는 모순에 직면했습니다.

## Decision

Mock API 프리셋의 완벽한 실시간 동기화는 제한적인 자원 환경에서 불가능함을 인지하고, 완벽함 대신 아래와 같은 **점진적 완화(Mitigation) 및 커뮤니티 주도 피드백 루프 전략**을 채택합니다.

1. **상태 대신 시간(Time) 기반 신뢰도 제공**
   - 프리셋 데이터 모델에서 `status` 및 `verifiedCount` 필드를 제거하고, `lastVerifiedAt`(최종 확인일) 속성으로 대체합니다.
   - UI에 "검증됨/검증 전" 대신 "공식문서 기반 (최종 확인일: YYYY.MM.DD)"를 표기하여, 사용자 스스로 데이터의 최신성과 신뢰도를 판단하도록 합니다.
2. **마찰 없는(Frictionless) 원클릭 제보 루프 구축**
   - 사용자가 스펙 불일치를 발견했을 때 곧바로 제보할 수 있도록 UI에 "잘못된 스펙 제보하기" 버튼을 배치합니다.
   - 버튼 클릭 시 현재 설정된 페이로드가 클립보드에 자동 복사되며, 사전에 구성된 GitHub Issue Template(`preset_drift.md`)으로 즉시 연결되어 즉각적인 기여를 유도합니다.

## Status

**Accepted**

## Consequences

- **Positive:**
  - 사용자에게 맹목적인 신뢰("검증됨")를 부여하는 대신 팩트("확인일")를 제공함으로써, 예상치 못한 프로덕션 장애에 대한 서비스의 책임 소재를 덜고 사용자 스스로 방어적인 테스트를 하도록 돕습니다.
  - 마찰을 최소화한 피드백 루프를 통해 커뮤니티 기여를 통한 유지보수(Crowdsourced Maintenance) 체계가 강화됩니다.
- **Negative:**
  - 프리셋 스펙을 업데이트하거나 신규 추가할 때 기여자가 수동으로 `lastVerifiedAt`을 갱신해야 합니다. (이 부분은 DEVELOPMENT.md 가이드라인에 명시)
