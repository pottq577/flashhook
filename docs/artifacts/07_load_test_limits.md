# 시스템 한계치 및 부하 테스트 설계 분석

FlashHook은 가입 없이 24시간 동안 임시 엔드포인트를 발급받고 웹훅을 실시간(SSE)으로 수신하는 SaaS 플랫폼입니다. \
본 문서는 현재 구현된 아키텍처(Spring Boot 4.x, MongoDB, Redis)를 바탕으로 **동시 접속자 500명** 및 **500 TPS** 라는 스트레스 상황에서의 시스템 한계를 수학적으로 도출하고 분석합니다.

---

## 1. 커넥션 유지 한계

**목표치**: 동시 접속자 500명 (500개의 활성화된 SSE 스트림)

FlashHook의 대시보드는 서버와 SSE 커넥션을 맺고 실시간으로 로그를 수신합니다. \
과거의 동기식 I/O 였다면 500개의 접속은 500개의 톰캣 작업 스레드를 독점하여 서버를 마비시켰을 것입니다. \
그러나 FlashHook은 Spring의 `SseEmitter`와 Non-blocking I/O를 활용해 비동기로 스트림을 처리합니다.

- Tomcat의 기본 최대 커넥션 수용량은 8,192개이며, 운영체제의 Open File Descriptors 설정(일반적으로 65,535)과 JVM 힙 메모리(객체당 수 KB)의 제한을 받습니다.
- 시스템의 비동기 구조 덕분에 **500명의 동시 접속은 단일 JVM 인스턴스에서 스레드 고갈 없이 매우 안정적(10% 미만의 부하)으로 방어 가능한 수치**입니다.

---

## 2. 처리량 병목 구간 분석

**목표치**: 웹훅 수신 500 TPS

웹훅이 1건 수신될 때 시스템은 다음 작업들을 수행합니다.

1. MongoDB에 로그 다큐먼트 Insert.
2. MongoDB에 해당 엔드포인트의 통계(로그 개수, 용량)를 `findAndModify`로 원자적 업데이트.
3. Redis Lua 스크립트를 통한 Rate Limit 검증.
4. `ApplicationEvent`를 발행하여 스레드 풀(`taskExecutor`)을 통해 SSE로 비동기 전파.

초당 500건의 요청이 인입될 때, 시스템 내의 **세 가지 주요 병목 지점**을 맞닥뜨리게 됩니다.

### A. 데이터베이스 I/O 처리량

`application.yaml`에 설정된 MongoDB 커넥션 풀은 최대 100개(`maxPoolSize=100`)입니다. \
리틀의 법칙($L = \lambda W$)에 따라, 1건의 DB 업데이트(Insert + findAndModify)가 총 5ms 소요된다고 가정할 때, 커넥션 풀 100개가 감당할 수 있는 최대 이론적 TPS는 약 10,000 TPS(100 / 0.005 / 2)입니다. \
실제 서비스 특성상 트래픽은 다수의 엔드포인트로 자연스럽게 분산 유입되므로, 단일 다큐먼트에 대한 쓰기 락 경합 없이 MongoDB는 500 TPS 수준의 트래픽을 아무런 병목 없이 견고하게 소화해냅니다.

### B. 비동기 스레드 풀 고갈 ⚠️

현재 `AsyncConfig.java`에 설정된 SSE 전파용 스레드 풀은 `core=4, max=8, queue=100`으로 매우 작게 설정되어 있습니다.

- 네트워크 지연 등을 포함해 스레드 8개가 1개의 이벤트를 전송하는 데 평균 20ms가 걸린다고 가정하면, 초당 최대 처리량은 400 TPS(`8 / 0.02`)입니다.
- 500 TPS가 유입되면 스레드 처리 속도보다 인입 속도가 빠르므로, 1초 만에 100개의 대기열(Queue)이 가득 차고 `TaskRejectedException`이 발생하며 이벤트가 유실됩니다.
- **해결책**: 500 TPS 이상의 고부하를 견디기 위해서는 스레드 풀(`max`)과 큐(`queue`) 사이즈를 각각 50, 1000 이상으로 튜닝해야 합니다.

### C. 어뷰징 방어벽

현재 시스템은 Redis를 통해 **웹훅 수신을 100회/분(약 1.6 TPS)**으로 강력하게 제한하고 있습니다. \
이는 단일 클라이언트의 악의적인 공격을 막기 위한 필수 방어벽이나, 부하 테스트 진행 시 가장 먼저 429 에러를 뱉어내는 장벽이 되므로 테스트 시에는 이를 해제해야 합니다.

---

## 3. 요약 및 시사점

FlashHook의 단일 인스턴스 구조는 500명의 대규모 실시간 모니터링 사용자(SSE)를 수용하기에는 충분히 견고하게 설계되었습니다. \
초당 500건에 달하는 대규모 쓰기 부하를 안정적으로 소화하기 위해서는 데이터베이스 병목보다는 비동기 이벤트 큐의 적체 현상이 더 큰 문제가 됩니다. \
이를 해결하기 위해 **(1) 부하 테스트를 위한 Rate Limit의 임시 완화, (2) 비동기 스레드 풀의 대폭적인 튜닝**이라는 아키텍처 레벨의 최적화가 동반되어야 함을 수학적으로 증명할 수 있습니다.
