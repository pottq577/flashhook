# 부하 테스트 실행 계획 (k6)

## 0. 목표와 판단 기준

- **1차 목표**: 문서 예측(SSE 팬아웃 ~400 TPS 부근 유실)을 **실측으로 검증**하고, 병목 지점과 임계 TPS 를 수치화한다.
- **2차 목표**: 병목 완화(스레드 풀 튜닝)의 효과를 **동일 시나리오 전/후 비교**로 증명한다.
- **판단 기준(예시, 실측으로 조정)**:
  - 웹훅 수신 응답 `http_req_duration` p95 < 300ms, p99 < 800ms
  - **SSE 이벤트 유실률 < 0.1%**, SSE 전파 지연 p95 < 1s
  - 오류율(429 제외) < 0.5%
  - CPU/힙이 포화(예: 힙 사용 > 85% 지속)되지 않을 것
- **⚠️ 개선 판단은 두 지표를 _동시에_ 만족해야 한다**:
  - "웹훅 응답 p95/p99"와 "SSE 유실률/전파 지연"을 함께 본다.
  - 한쪽만 좋아진 결과(예: 유실률은 줄었으나 웹훅이 느려짐)를 "개선"으로 오판하지 않는다.
  - 특히 Phase 2 의 `CallerRunsPolicy` 후보는 이 트레이드오프가 표면화되므로 아래 §3 Phase 2 관찰 항목을 반드시 함께 확인한다.

## 1. 측정 원칙

- **429 는 실패와 분리 집계**한다(레이트리밋은 정상 동작). k6 커스텀 metric 으로 별도 카운트.
- **웹훅 응답 지연 ≠ SSE 전파 지연**. 두 지표를 독립적으로 측정한다(07 문서 §0 참조).
  - SSE 전파 지연/유실은 웹훅 body 에 `sentAt` 타임스탬프를 심고, SSE 로 도달한 이벤트에서 이를 비교해 산출한다(수신 건수 vs 도달 건수 = 유실률).
- **서버측 지표를 항상 함께 본다**: Actuator/Prometheus(`:9090` `/actuator/prometheus`)로 JVM 힙/GC, Tomcat 스레드, Mongo 커넥션 풀, `taskExecutor` 큐 적체, 커스텀 카운터를 상관 분석.
- **Redis 응답 지연 별도 확인**: `RedisConfig.java`는 Lettuce 기본 풀(단일 공유 커넥션)을 사용하며 풀 크기를 별도 지정하지 않음. 고 TPS 시 Redis Lua 스크립트 실행 지연이 레이트리밋 응답 시간에 포함되므로 `redis_command_duration`을 별도 관찰 항목으로 수집한다.
  > 💡 **Phase 1 실측 교훈**: Spring Boot 기본 설정에서는 Lettuce의 상세 커맨드 지표가 노출되지 않아 실측이 불가능했습니다. 향후 정밀 튜닝을 위해서는 Redis 지표 노출을 위한 추가 설정 작업(백로그)이 선행되어야 합니다.
- 부하 생성기(k6) 자체가 병목이 되지 않도록 클라이언트 리소스도 모니터링.

## 2. 시나리오 (k6 executors)

| ID  | 시나리오        | executor                              | 부하     | 관찰                                                                                       |
| --- | --------------- | ------------------------------------- | -------- | ------------------------------------------------------------------------------------------ |
| S0  | Smoke           | `constant-vus` (1 VU, 1m)             | 최소     | 스크립트/경로 정합성                                                                       |
| S1  | 웹훅 수신 용량  | `ramping-arrival-rate` (→ 800 TPS)    | 점증     | 응답 지연, DB, **팬아웃 임계**                                                             |
| S2  | SSE 팬아웃      | SSE 구독 유지 + S1 병행 (구성은 §2.1) | 혼합     | **전파 지연/유실률**                                                                       |
| S3  | SSE 연결 스케일 | 500+ 동시 SSE 유지(Soak 30m+)         | 지속     | 연결 안정성/누수/heartbeat (💡 Phase 1에서는 1분 Smoke만 진행. 30분 Soak은 추후 별도 진행) |
| S4  | 엔드포인트 생성 | `ramping-arrival-rate`                | 스파이크 | 생성 처리량, 429 경계                                                                      |
| S5  | 로그 조회       | `constant-arrival-rate`               | 일정     | 커서 페이징 + 캐시 효율                                                                    |
| S6  | Replay          | `constant-arrival-rate`               | 낮음     | SSRF 검증 오버헤드, 싱크 수신                                                              |
| S7  | 레이트리밋 동작 | 디폴트 한도, 초과 인입                | -        | 429 비율/정확도, 블랙리스트                                                                |
| S8  | 로그 상한 동작  | 디폴트 상한(500/5MB) 도달             | -        | 상한 도달 후 거부/정리 성능                                                                |

> S2/S3 는 k6 순정 SSE 지원이 약하므로 **`xk6-sse` 확장**으로 빌드하거나, 별도 SSE 클라이언트(Node/k6 browser)로 보완한다.

### 2.1 S2 구독 구성 (팬아웃 집중도)

07 §2.B 의 병목 산식은 **태스크 1건 비용 = (엔드포인트당 구독자 수 × 1회 send 시간)** 이므로, "엔드포인트당 구독자 수"를 시나리오에 명시적으로 고정한다.

| 구성                       | 엔드포인트 × 구독자 | 총 커넥션 | 목적                                                           |
| -------------------------- | ------------------- | --------- | -------------------------------------------------------------- |
| **S2-a (기본)**            | 500 EP × 1          | 500       | 트래픽 균등 분산, "동시 500명" 기준선                          |
| **S2-b (집중, 권장 추가)** | 100 EP × 5          | 500       | 소수 인기 EP 에 다수 구독 — 프로덕션에서 더 위험한 팬아웃 패턴 |

> S2-b 는 같은 총 커넥션(500)이라도 이벤트당 순차 send 횟수가 5배라 taskExecutor 태스크 비용이 커진다. 동일 TPS 에서 S2-a 대비 임계가 더 낮게 나오는지 비교한다.

### 2.2 S2 slow consumer (심화, head-of-line blocking)

팬아웃이 **태스크 내부에서 구독자별 순차 blocking send** 이므로, 한 구독자가 느리면 같은 EP의 나머지 구독자 전달까지 지연되는 head-of-line blocking 이 가능하다(07 §3). \
S2-b 에 **구독자 1~2개가 의도적으로 읽기를 지연**(느린 클라이언트)하는 케이스를 추가해, 정상 구독자의 전파 지연이 함께 악화되는지 검증한다. (필수 아님, 아키텍처 약점 검증용)

## 3. 단계별 실행 순서 (Phase)

### Phase 0 — 환경 준비 (로컬)

- `docker-compose up -d mongodb redis` (레포 제공 구성 사용).
- 백엔드를 `local` 프로파일로 기동(필수 env: `FLASHHOOK_SECRET_KEY`, `FLASHHOOK_ADMIN_SECRET_KEY`).
- **부하용 프로파일 `application-load.yaml` 신규**: Rate Limit·로그 상한을 크게 상향(용량 측정용).
- Prometheus 를 `:9090/actuator/prometheus` 로 스크레이프(또는 k6 실행 중 주기 수집).
- `xk6-sse` 로 k6 바이너리 빌드, Replay 대상용 **싱크 서버**(요청 수신·카운트) 기동.
  > 💡 **Phase 0 적용 팁**: S6 Replay 테스트 시 SSRF 검증(로컬/사설망 IP 차단) 로직을 코드 수정 없이 우회하여 테스트하려면, `198.51.100.1`(RFC 5737 더미 대역)과 같은 가상 인터페이스에 싱크 서버를 바인딩하여 테스트합니다.

### Phase 1 — 로컬 측정 (디폴트 async 풀) **[완료]**

- 1a: S0 Smoke 로 경로/스크립트 검증.
- 1b: **S1 + S2(S2-a, 여유 시 S2-b)를 디폴트(`max8/queue100`)로 실행** → SSE 전파 지연이 급격히 벌어지거나 유실이 시작되는 **임계 TPS 확인**(예측: ~400 TPS 부근). 순수 write 성능은 로그 상한 상향 상태로 측정.
  - **⚠️ 유실 집계 grace period**: 트래픽 발생을 멈춘 뒤 **SSE 커넥션을 수십 초 더 열어두고** 큐에 남은 잔여 이벤트를 마저 수신한 다음 최종 유실률을 집계한다. 그렇지 않으면 "아직 도착 전"인 이벤트를 "유실"로 오집계한다(디폴트 설정은 큐 적체가 커 오차가 특히 큼).
  - 💡 **후속 측정 팁**: `executor.rejected.tasks`를 수집할 때, 현재는 웹훅 팬아웃과 Heartbeat 거부가 혼재되어 카운트됩니다. 향후 측정 시에는 `task_type` 태그를 나누어 수집해야 정확한 유실 원인 파악이 가능합니다.
- 1c: S3 SSE 연결 스케일 Soak(누수/heartbeat 안정성). (※ 1분 단위 스모크만 완료, 장기 Soak은 미진행)
- 1d: **S7 레이트리밋 동작 검증**(디폴트 한도 복원, 429 분리 집계, 블랙리스트 동작).
- 1e: **S8 로그 상한 동작**(디폴트 상한 복원, 도달 후 거동 관찰).

> 💡 **Phase 1 실측 요약**: S1 600 TPS 피크 도달, S2 유실률 0.031%로 시스템이 예측치보다 훨씬 견고함이 실증되었습니다. (상세 내용은 `07_load_test_limits.md` §6 참조)

### Phase 2 — 튜닝 후 재측정 (로컬) **[우선순위 하향]**

> 💡 **Note**: Phase 1의 실측 결과, 400 TPS 부근의 극한 부하에서도 SSE 이벤트 유실률이 0.031%에 그쳤습니다. 따라서 디폴트 설정(max8/queue100)으로도 운영 요건(500명, 500 TPS)을 충분히 상회하여 방어할 수 있음이 입증되었으므로, **아래의 스레드 풀 튜닝 작업은 필수 요건에서 선택적 백로그로 우선순위가 하향**되었습니다.

- 후보 정책을 **각각 별도로** 측정·비교한다(하나로 뭉뚱그리지 않는다):
  - **후보 A — `AbortPolicy` 유지 + 풀/큐 상향**(예: `max=50`, `queue=1000`): 유실을 큐로 흡수.
  - **후보 B — `CallerRunsPolicy`**: 큐 포화 시 이벤트 발행 스레드(=Tomcat 워커, 웹훅 요청 처리 스레드)가 직접 순차 send 를 떠맡음 → 유실 대신 지연을 택하는 트레이드오프.
- **⚠️ 후보 B 는 07 §0 전제("웹훅 응답 지연 ≠ SSE 전파 지연")를 깨뜨린다.** 정책 발동 순간 웹훅 p95/p99 가 SSE 팬아웃 지연을 그대로 흡수하므로, **"웹훅 응답 지연 급증 여부"를 Phase 2 의 신규 관찰 항목으로 추가**한다.
- **1b/1c 를 동일 조건으로 재실행 → 전/후 비교**. 판정은 §0 원칙대로 **웹훅 p95/p99 와 SSE 유실률/지연을 동시에** 만족하는 후보를 채택(임계 TPS 상승 + 유실률 감소 + 웹훅 지연 비악화).
- 주의: 스레드 과다는 역효과. 몇 가지 후보값을 실측 비교해 최적값 선택.

### Phase 3 — 스테이징 재검증 (스펙 동일 전제)

- 로컬에서 나온 **절대 수치는 참고용**(개발 머신 ≠ Oracle ARM 단일 인스턴스).
- 스테이징 스펙이 프로덕션과 동일함을 먼저 확인한 뒤, 최종 임계치/튜닝값을 재검증.
- **선행 확인**: 스테이징이 Cloudflare 를 우회해 직접 노출되는지(레이트리밋 우회 리스크, 07 문서 §4 주의).

## 6. 리스크 및 주의

- **프로덕션 직접 부하 금지**(단일 인스턴스, 실사용자 영향). 스테이징/로컬만 사용.
- 부하 생성기 병목·네트워크 한계로 인한 오측 방지(클라이언트 지표 동시 관찰).
- 파괴적 엔드포인트(`test-endpoints`)는 로컬에서만 활성; 스테이징/운영 비활성 유지.
- 측정 오염 요인(로그 상한 도달, TTL 만료, 캐시 워밍업)을 시나리오 설계에 반영.
